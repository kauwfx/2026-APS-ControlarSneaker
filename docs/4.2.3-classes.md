# 4.2.3 Modelagem de Classes

## Dos substantivos às classes

As classes saem dos substantivos. A fonte principal é o fluxo de Registrar pedido, especificado na 4.2.2. Cada coisa que o ator informa ou que o sistema confirma é uma coisa que o sistema precisa lembrar. A segunda fonte é a lista de requisitos da 4.2.1. O que aparece nas duas vira classe com mais confiança.

Nem todo substantivo vira classe. Três filtros: o que é detalhe de outra coisa vira atributo (o telefone é detalhe do cliente). O que é interface não entra (tela, botão, relatório). O que está fora do sistema também não.

| Substantivo | De onde veio | Vira | Por quê |
|---|---|---|---|
| cliente | passo 1 do fluxo, HU01, RF01 | classe **Cliente** | o sistema guarda quem ele é, seu endereço e dados de contato para entregas |
| vendedor / administrador | ator da 4.2.2, pré-condição, RNF02 | classe **Usuario** e classe **Vendedor** | o sistema precisa saber quem é o usuário autenticado que registra pedidos e atualiza status |
| nome, telefone, endereço | passo 2 do fluxo ("apresenta os dados cadastrados"), RF01 | atributos de **Cliente** | são os detalhes cadastrais necessários para contato e envio do tênis |
| pedido | passo 3 e 7 do fluxo, HU02, RF02, RF03 | classe **Pedido** | é a venda registrada: vincula o cliente aos itens e à sua entrega |
| produto / sneaker | escopo da 4.1, HU02, RF02 | classe **Produto** | o tênis comercializado pela loja que compõe o pedido |
| entrega / status | passo 5 e 6 do fluxo, HU04, RF04, RF05 | classe **Entrega** | o registro com endereço, status, datas e histórico de transporte |
| dados da entrega | passo 5 ("informa os dados da entrega") | atributos de **Entrega** | são detalhes como endereço final e status da entrega, não algo isolado |

## Classes

Cinco classes cobrem o escopo do ControlarSneaker. A classe `Vendedor` herda de `Usuario` para validar o perfil restrito de acesso exigido no `RNF02`. Cada atributo e operação possui origem rastreável na 4.2.2 ou na 4.2.1.

| Classe | Atributos | Operações | Veio de |
|---|---|---|---|
| **Usuario** | - nome: String, - login: String, - senha: String | + autenticar(): boolean | RNF02 (acesso restrito ao perfil cadastrado) |
| **Vendedor** | _herda de Usuario_ | + registrarPedido(): boolean | Ator da 4.2.2, HU02 e passo 7 do fluxo principal |
| **Cliente** | - nome: String, - telefone: String, - endereco: String | + consultarHistorico(): List | passo 1, 2 do fluxo, HU01, HU05, RF01 e RF05 |
| **Produto** | - codigo: String, - modelo: String, - tamanho: int, - preco: double | + estaDisponivel(): boolean | HU02, RF02 (dados do pedido de tênis) |
| **Pedido** | - numero: int, - dataCriacao: Data, - valorTotal: double | + calcularTotal(): double, + cancelar(): void | passos 3, 7 do fluxo, HU02, HU03, RF02 e RF03 |
| **Entrega** | - codigoRastreio: String, - status: String, - dataEnvio: Data | + atualizarStatus(): void, + estaConcluida(): boolean | passos 5, 6 do fluxo, HU04, HU05, RF04 e RF05 |

## Diagrama de classes

**Figura 2 – Diagrama de classes do ControlarSneaker**

![Diagrama de classes](../diagramas/classes.png)

Fonte: Autoria própria (2026).

A Figura 2 apresenta as cinco classes do ControlarSneaker interligadas por associações, herança e composição.

As **associações** representam as ligações diretas do domínio da loja. Um `Cliente` faz zero ou vários (`0..*`) `Pedido`, enquanto cada `Pedido` pertence a exatamente um (`1`) `Cliente`. O `Vendedor` registra zero ou vários (`0..*`) `Pedido`, e cada `Pedido` é registrado por exatamente um (`1`) `Vendedor`. Cada `Pedido` é composto por um ou vários (`1..*`) `Produto`.

A **herança** é representada pelo triângulo vazado apontando para `Usuario`. `Vendedor` é um tipo de usuário do sistema, herdando nome, login e senha, mantendo centralizada a regra de autenticação (`RNF02`).

A **composição** é representada pelo losango cheio do lado de `Pedido` na relação com `Entrega`: a entrega é parte integrante do pedido. Se um registro de pedido for removido do sistema, a sua entrega associada deixa de existir (morre junto). ❓ A confirmar com o cliente Kauê: se um pedido for cancelado antes da separação, a entrega é alterada para o status "Cancelada" ou o objeto de entrega nem chega a ser criado?

Não há **agregação** no modelo, pois não existem entregas ou itens transitando soltos sem vínculo com um pedido ou cliente cadastrado.

## Teste de objetos

Um diagrama de classes é uma promessa sobre o mundo. O jeito de testar essa promessa é pegar uma situação real descrita pelo Kauê e desenhar os objetos correspondentes.

A situação: O vendedor Kauê registra o pedido #101 para o cliente Matheus, contendo um tênis "Nike Dunk Low" (tamanho 41). A entrega é gerada com o status "Pendente" no endereço informado.

**Figura 3 – Diagrama de objetos: registro de um pedido na loja**

![Diagrama de objetos do ControlarSneaker](../diagramas/objetos.png)

Fonte: Autoria própria (2026).

| Objeto | Classe | Valores |
|---|---|---|
| `kaue` | Vendedor | nome = "Kauê Silva", login = "kaue.admin" |
| `matheus` | Cliente | nome = "Matheus Oliveira", telefone = "(42) 99888-1234", endereco = "Rua Balduíno Taques, 500" |
| `dunkLow` | Produto | codigo = "SNK-041", modelo = "Nike Dunk Low", tamanho = 41, preco = 899.90 |
| `ped101` | Pedido | numero = 101, dataCriacao = "26/10/2026", valorTotal = 899.90 |
| `ent101` | Entrega | codigoRastreio = "TRK-101BR", status = "Pendente", dataEnvio = "26/10/2026" |

**Ligações:** `kaue` e `ped101`, `matheus` e `ped101`, `ped101` e `dunkLow`, `ped101` e `ent101`.

**O que o teste confirma**

- **Um cliente faz vários pedidos.** O cliente `matheus` está associado ao pedido `ped101` sem duplicar seu cadastro de endereço (`RF01`).
- **Cada pedido possui um responsável e um destinatário.** O pedido `ped101` liga-se exatamente a um `Vendedor` (`kaue`) e a um `Cliente` (`matheus`).
- **A entrega reflete a solicitação do cliente.** A entrega `ent101` guarda o endereço e o status "Pendente" para viabilizar a listagem exigida pelo `RF03`.
- **O tênis está associado ao pedido.** O sneaker `dunkLow` está vinculado ao `ped101` mantendo o valor contratado.

## Rastreabilidade com a 4.2.2

| Operação ou atributo | Classe | De onde veio |
|---|---|---|
| autenticar() | Usuario | RNF02: acesso e alterações restritos ao perfil cadastrado |
| registrarPedido() | Vendedor | passo 7 do fluxo principal de Registrar pedido, HU02, RF02 |
| consultarHistorico() | Cliente | passo 2 do fluxo, HU05 e RF05 (consultar histórico) |
| estaDisponivel() | Produto | passo 4 do fluxo (verificação de dados do pedido) |
| calcularTotal(), cancelar() | Pedido | passos 3 e 7 de Registrar pedido, HU03, RF02, RF03 |
| atualizarStatus(), estaConcluida() | Entrega | passos 5 e 6 do fluxo, HU04, RF04 (atualizar status) |

**Toda operação tem origem.** Nenhuma operação apareceu sem respaldar os passos da especificação da 4.2.2 ou da lista de requisitos da 4.2.1.

**Todo passo do sistema tem casa.** Os passos 2, 4, 6 e 8 do fluxo principal (onde o sistema apresenta, verifica ou registra) foram mapeados em métodos das classes `Cliente`, `Produto`, `Entrega` e `Pedido`.

**O que a modelagem mudou.** A especificação detalhada da 4.2.2 exigiu criar a classe `Produto` (sneaker) separada de `Pedido` para representar o item comercializado. Além disso, a `Entrega` virou uma classe própria com composição em `Pedido`, garantindo o atendimento direto aos requisitos `RF03` (listar pendentes por endereço) e `RF04` (atualizar status).
